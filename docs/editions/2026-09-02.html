AI SDLC Radar

A focused briefing on AI software development, modern SDLC practices, QA, test automation, and open source tooling.

Main signal

The strongest movement today is not toward simply adding more autonomous agents. It is toward making agent execution testable, isolated, and governable.

Agent reasons → tool interface executes → evidence is captured → deterministic checks validate → controlled write path applies changes

For QA, the agent itself is no longer the only thing under test. The tools, protocols, execution environment, and evidence path are becoming explicit test surfaces.

1. MCP servers are becoming first class test targets

Experiment now

test-mcp is an open source CLI for end to end testing of MCP servers and agents. It lets teams define natural language flows and assertions in YAML, run them headlessly, and produce repeatable pass or fail results against local or remote MCP servers.

The important signal is architectural. MCP is increasingly being treated like an API surface that needs its own contract tests, regression suite, traceability, and CI integration rather than as invisible agent plumbing.

Assessment opportunity: add MCP tool coverage, tool contract testing, trace capture, and failure diagnostics to AI readiness assessments.

2. Electron apps are getting agent native UX testing

Watch closely

Electron Stagewright is an emerging MCP server aimed specifically at agent driven testing of real Electron applications. It exposes accessibility based refs, retrying assertions, multiwindow handling, native menus, dialogs, diagnostics, and packaged application workflows.

Why it matters: if this pattern matures, agentic testing could expand beyond web UI into desktop products without relying on fragile coordinate based automation.

3. GitHub is formalizing agentic workflows as a governed CI layer

Experiment now

GitHub's Agentic Workflows documentation positions gh-aw as a layer that compiles natural language repository automation into standard GitHub Actions workflows with controls for permissions, tools, sandboxing, and writes.

GitHub explicitly recommends keeping builds, tests, linting, deployments, and other reproducible checks deterministic, while using agents for reasoning heavy tasks such as investigation, interpretation, and generation.

  • Agents investigate failures, propose changes, and interpret repository context.
  • Deterministic CI executes builds, tests, linting, security scans, and release gates.
  • Write access is controlled through constrained output paths rather than broad agent permissions.

4. Coding agent workspaces are becoming branch isolated team environments

Watch closely

Agor is a self hosted workspace that runs coding agents on isolated Git branches, with each branch acting as its own working directory, development environment, and conversation context.

The specific project is early, but the model is worth watching: branch isolation as the unit of agent execution. This gives teams a natural rollback boundary, clearer provenance, easier parallelism, and a cleaner path to review before agent generated changes reach shared branches.

Emerging pattern

  • MCP and other agent tool interfaces are becoming explicit QA surfaces.
  • Agent execution environments are becoming isolated by default.
  • Deterministic CI is remaining the final source of truth for verification.
  • Agent generated actions increasingly need observable evidence rather than opaque success messages.
  • The practical architecture is shifting from agent does everything to agent reasons inside a governed execution system.

Consulting angle

  • Can agent tool interfaces be tested independently from the model?
  • Are MCP servers covered by repeatable contract and regression tests?
  • Does every agent run execute inside an isolated workspace or branch?
  • Are builds, tests, security checks, and release gates still deterministic?
  • Can the team reconstruct why an agent took an action from traces and artifacts?
  • Are agent writes constrained through explicit policy controlled paths?
  • Can competing agent outputs be compared using objective engineering evidence?

The consulting opportunity is increasingly about designing the verification and execution architecture around coding agents, not simply helping teams choose a coding assistant.
