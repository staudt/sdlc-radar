Agent controls have to fail closed

Back to Radar

October 12, 2026

Today's theme is whether agent controls fail closed: hooks that approve or block actions, sandboxes built from files an attacker may control, and background agent fleets that spend money on their own, all of which decide whether your source code, credentials, and cloud bill stay under your control when something goes wrong.

Main signal

Agent harnesses are being asked what happens when a control itself breaks, times out, or is tampered with. A security hook that fails to start can silently let a risky command run unless you opt in to blocking, and a sandbox can be weakened by a writable helper executable or a search-tool config file. The same week, agents gained the ability to write programs that launch up to 1,000 sub-agents, so a control that fails open now fails at fleet scale.

"A security hook that fails open is a suggestion: test what your agent can do when the control crashes."

Quick News

  • GitHub Agentic Workflows v0.91.8 (Oct 11) renders agent sessions as full elapsed-time timelines across Copilot, Codex, Claude, and Gemini engines.
  • Odoo MCP (CVE-2026-108861, per VulDB) lets a client read denied fields through its execute_method tool, bypassing field-level access controls in versions 1.0.0 to 1.3.2.
  • Inspect AI 0.3.278 (Oct 9) extends tool review to cover handoff() calls between agents.

1. Claude Code hooks can now fail closed Production now

Layer: policy, evidence

Claude Code 2.1.295 (Oct 8) adds onFailure: "block" for command and HTTP hooks, so an action is blocked when its hook cannot start, times out, or exits unexpectedly instead of proceeding. Version 2.1.296 (Oct 9) fixes a BASH_ARGV0 permission bypass, an interrupt that let an unchecked prompt past a UserPromptSubmit hook, and headless sessions starting MCP servers that were disabled for a folder.

Why it matters: A hook is only a control if its failure blocks the action, so set fail-closed on every policy hook and test it by breaking the hook on purpose.

2. Sandbox hardening now covers the sandbox's own inputs Experiment now

Layer: execution, policy

Codex 0.162.0 (Oct 8, with 0.162.1 following Oct 9) rejects writable executables used to build its sandbox, including bubblewrap binaries found on PATH, and stops ripgrep configuration from weakening deny-glob masks. It also adds managed Git worktree tools for trusted projects behind a feature flag.

Why it matters: Sandbox tests should attack what the sandbox is built from, such as PATH entries and tool config files, because an agent that can write those can loosen its own limits.

3. Agents can now write programs that run agent fleets Watch closely

Layer: orchestration, evidence

Anthropic released Dynamic Workflows in beta for Managed Agents on Oct 9: the agent writes a workflow program that runs agents in phases in the background, and the workflow runs documentation sets a 1,000-agent limit per run, a 24-hour default lifetime, ten open runs per session, and pauses every run when the session budget is reached. A run has no price of its own, and per-run usage must be assembled by adding up thread token counts. Claude Code 2.1.296 adds a matching CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL setting to run all workflow agents on one model.

Why it matters: The orchestration plan is now generated code you did not write, so require a budget, a thread limit, and a per-run usage record before any team enables it.

Bet tracker

Bet: Agent control planes will move outside the agent's own process and network reach. Strengthening. Claude Code's managed-settings hooks now have an explicit fail-closed mode, and Codex refuses sandbox executables the agent could have written.

Bet: Cost, model strength, and independent verification will be optimized together at runtime through workflow routing. Strengthening. A session budget that pauses every open workflow run and a single-model setting for workflow agents make cost routing a configured policy rather than a convention.

Consulting angle

Ask this week: If a policy hook, sandbox helper, or budget limit in your agent harness crashes or is misconfigured, does the agent stop or keep going, and has anyone tested that?
