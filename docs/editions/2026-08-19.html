AI SDLC Radar

Main signal

The strongest signal is the operationalization of agents inside the SDLC, particularly testing, CI investigation, repository maintenance, and controlled automation. Several projects are converging on the same architecture: deterministic automation underneath, agents for reasoning, and explicit security boundaries around anything that can modify code or infrastructure.

1. Playwright is turning test automation into an agent skill

Experiment now

Microsoft released a significant update to microsoft/playwright-cli. The important addition is a spec driven testing skill that guides coding agents through a plan → generate → heal workflow from a written specification. The CLI exposes test execution, debugging, mocking, tracing, browser sessions, test generation, and healing as agent consumable capabilities.

For coding agents, Playwright recommends CLI plus Skills over MCP in many cases because MCP tool schemas and accessibility snapshots consume substantial context. MCP is positioned more toward persistent exploratory loops and long running self healing behavior.

Coding agent → Playwright Skill → CLI → browser

QA implication: the interesting future is probably not “AI writes Playwright tests.” It is a testing skill embedded into a coding agent that can examine requirements, inspect the application, generate tests, run them, diagnose failures, and repair them.

2. Agentic CI is becoming a real SDLC layer

Experiment now

GitHub Agentic Workflows lets teams define repository agents in Markdown, compile them into GitHub Actions workflows, and run them with multiple coding agent providers. GitHub recommends keeping deterministic operations such as builds, tests, linting, and deployment in normal Actions while using agents for work requiring interpretation, such as CI investigation, code review, and issue triage.

The Safe Outputs architecture allows agents to propose PRs, comments, labels, and other mutations without giving the reasoning agent direct write permissions.

Agent reads → agent reasons → agent proposes → security or policy layer validates → deterministic system executes

That separation may become a standard pattern for enterprise agentic SDLC.

3. Azure DevOps has an open source agentic workflow implementation

Experiment if you assess Azure DevOps clients

githubnext/ado-aw applies a similar model to Azure DevOps. Agent workflows are written in Markdown and compiled into multi stage Azure Pipelines. The architecture deliberately isolates the agent from write credentials, with output passing through a separate controlled executor.

A useful AI readiness assessment question is: can this organization's CI/CD architecture safely host reasoning agents without granting those agents direct mutation privileges?

4. SWE-ABS exposes a major problem with evaluating coding agents

Very important for QA thinking

SWE-ABS attacks a weakness in coding agent benchmarks that QA engineers should immediately recognize: a patch passing tests does not prove the patch is correct if the tests are weak.

SWE-ABS automatically generates additional tests, generates mutation patches, checks whether those tests distinguish correct implementations from subtly incorrect ones, and strengthens the benchmark when mutations survive.

AI generated implementation → independent test generation → mutation or adversarial validation → quality gate

This looks much more like modern QA engineering than simply asking a model to write unit tests.

5. MCP tooling is becoming testable infrastructure

Watch closely and experiment

The official MCP Inspector has evolved into a developer and CI tool with Web, CLI, and terminal interfaces. This matters because MCP servers are effectively becoming APIs for agents.

They will increasingly need:

  • contract testing
  • security testing
  • compatibility testing
  • CI validation
  • observability
  • version management

MCP-Universe attacks the adjacent problem of evaluating agents that use MCP tools.

Emerging pattern

  • Skills and CLI for short, code oriented agent operations
  • MCP for persistent or rich tool interactions
  • Deterministic CI for reproducible verification
  • Agents for investigation, planning, and interpretation
  • Policy layers between agent decisions and write operations
  • Adversarial evaluation rather than trusting successful test execution

That combination is substantially more important than any single new AI testing product.

Consulting angle

A strong 2026 assessment should increasingly examine agent readiness: whether requirements and repositories provide sufficient machine readable context, whether tests can serve as reliable agent feedback, whether CI exposes useful diagnostics, whether AI generated changes undergo independent validation, whether MCP or tool permissions are controlled, and whether agents are separated from privileged execution.

There is also a modernization opportunity emerging beyond Selenium → Playwright:

Traditional automation → Playwright + agent consumable testing capabilities + CI quality gates + controlled autonomous maintenance
