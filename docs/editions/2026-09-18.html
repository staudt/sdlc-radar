AI SDLC Radar

Today’s strongest evidence is about a QA problem that becomes more important as agents gain more tools: testing one protected path is not enough when equivalent authority can be reached through several execution surfaces.

Main signal

Agent QA needs execution path coverage, not just feature coverage. A new empirical study of 157 established open source agent projects finds that safeguards are common, but equivalent routes to shell, files, browsers, plugins, credentials, and external APIs are not consistently controlled or tested. At the same time, enterprise AI measurement is becoming granular enough to distinguish which agentic development surfaces teams actually use.

1. A 157 project study exposes the agent QA coverage gap

Study closely

What changed: A new paper, A Large-Scale Empirical Study of Quality Assurance Practices and Gaps in AI Agents, examined repository-visible QA evidence across 157 open source LLM agent projects with at least 100 GitHub stars. The corpus includes software engineering agents, coding assistants, browser automation, research agents, and other agent applications.

Why it matters: The important finding is not that projects lack safeguards. Many have approvals, sandboxes, permissions, secret handling, and domain controls. The problem is consistency across execution paths. The study found overlapping action paths as a QA challenge in 152 of 157 projects, outbound network effects in 156, credential exposure concerns in 155, workspace boundary concerns in 153, and command execution concerns in 148. Agent-specific tests for boundary, adversarial, and multi-step tool-use failures remain rare.

That changes how an assessment should define coverage. If an agent can reach similar authority through a CLI, MCP server, browser, plugin, shell, API, or subagent, validating one route does not establish that the policy boundary holds across the others. The QA unit is increasingly the complete model-to-action path.

SDLC fit: agent architecture reviews, MCP and tool testing, security QA, browser automation, CI agent governance, and acceptance criteria for autonomous workflows.

2. GitHub makes agent adoption measurable by development surface

Experiment now

What changed: GitHub’s Copilot impact dashboard now reports 28-day feature engagement separately for code completion, agent edit, passive and active code review, cloud agent, Copilot CLI, and Copilot app. The same breakdown is available through enterprise and organization reporting APIs.

Why it matters: Enterprise AI adoption can now be measured as a portfolio of development behaviors rather than a single active-user number. For consulting assessments, this creates a more useful baseline: teams can distinguish autocomplete adoption from code review, local agent use, and delegated cloud work, then correlate those behaviors with delivery and quality evidence.

Maturity: The telemetry is production functionality in GitHub’s enterprise reporting stack. The harder problem is organizational: deciding which quality, flow, and risk measures should be paired with usage so adoption does not become the success metric by itself.

SDLC fit: AI adoption assessments, engineering productivity analysis, rollout governance, training strategy, and quality transformation measurement.

Emerging pattern

  • Agent QA must map every execution surface that can reach the same authority.
  • Safeguard presence is weaker evidence than safeguard consistency across paths.
  • Boundary, adversarial, and multi-step tests are still underrepresented in real agent projects.
  • Enterprise adoption telemetry is becoming specific enough to compare agentic development modes rather than treating all AI usage as equivalent.

Consulting angle

Add an execution-surface inventory to agent readiness assessments. For each sensitive capability, identify every route that can invoke it, the policy and sandbox controls on each route, the tests proving those controls, and the evidence retained after execution. Separately, use feature-level AI adoption telemetry as an input to assessment, but pair it with quality and delivery outcomes rather than presenting usage as value.

Today’s evidence strongly reinforces the current Radar’s emphasis on permissions, MCP as a QA surface, independent quality gates, and adversarial validation. It sharpens the assessment method, but does not yet require a new radar point or maturity change.
