Approvals that must survive a restart: honest exit codes, folder-bound commands, and blanket flags on resume

Back to Radar

November 4, 2026

Today's theme is whether an agent's approvals and failures hold up across a restart or resume: Claude Code 2.1.318 stops headless runs from reporting success after a cut-off reply and binds an approved shell command to its folder, while Copilot CLI pre-releases now honor a blanket-approval flag on resume, which decides whether your pipelines show green for unfinished work and whether commands run where someone approved them.

Main signal

Approvals, denials, and failure status are being made to hold across restarts, resumes, and connectors. Claude Code 2.1.318 stops claude -p from reporting success when an API error cut off a reply, refuses to run a command approved before a runner restart in a folder it was not approved for, and extends MCP denials to cloud connectors, while Copilot CLI 1.0.106-7 applies --yolo when a local session resumes. A job that passes on unfinished work, or a command that runs in an unapproved folder, ships changes nobody checked.

"An approval an agent holds should mean the same thing after a restart or a resume, or it is a standing permission nobody reviewed."

1. Claude Code stops reporting success when a reply was cut off Experiment now

Layer: evidence, verification

Claude Code 2.1.318 (Nov 4) fixes claude -p and Agent SDK sessions reporting success when an API error cut off a reply while a mod hooked turn.step, and a stopped reply finishing as a success in headless runs. Non-interactive launches also no longer replace a ~/.claude.json that is not valid JSON with defaults: the start fails and leaves the file as is. It follows 2.1.317 (Nov 3), which made lost transcripts exit 1.

Why it matters: A pipeline that gated on exit 0 could have merged work from a reply that never finished, so add a negative test that forces an API error mid-reply and asserts a non-zero exit.

2. Claude Code ties shell approvals to a folder and extends MCP denials to connectors Experiment now

Layer: policy, execution

In Claude Code 2.1.318, a shell command approved before a self-hosted runner or cloud session restart no longer runs in the session's start folder instead of the folder it was asked in, and if that folder cannot be entered it does not run. deniedMcpServers URL entries now also block Anthropic-provided servers whose upstream URL matches, and connectors in cloud sessions and on self-hosted runners, and /claude-api managed-agents-onboard defaults new agents' built-in tools to the auto permission policy.

Why it matters: Re-test your managed deny list against the connectors your teams actually use, because an MCP server you blocked by URL may have stayed reachable through one, and check runner restarts in your approval tests.

3. Copilot CLI applies blanket approval flags when a session resumes Watch closely

Layer: policy, orchestration

The GitHub Copilot CLI 1.0.106-7 pre-release (Nov 3) makes --yolo and --allow-all take effect when resuming a local session, and adds a /code command and a Fusion tier setting. The -6 pre-release (Nov 3) stops MCP content addressed only to the user from reaching the model. These are pre-releases and I read the release notes, not the code.

Why it matters: A script that resumes a session with the flag now gets every tool call auto-approved, so keep the flag out of shared wrappers and log which sessions ran with it.

Field lines

  • "A CI job that exits zero after an agent's reply was cut off by an API error is passing a delivery check on work that never finished." (Claude Code 2.1.318 release notes)
  • "A shell approval for a coding agent should name the folder it runs in, because a restart that changes the folder changes what was approved." (Claude Code 2.1.318 release notes)
  • "A blanket-approval flag such as yolo that survives a session resume needs an owner and a log, or a convenience becomes an unreviewed standing permission." (Copilot CLI 1.0.106-7 release notes)

Bet tracker

Strengthening: Agent control planes will move outside the agent's own process and network reach. Claude Code 2.1.318 makes deniedMcpServers block connectors in cloud sessions and on self-hosted runners, so the managed deny list, not the agent session, decides what stays reachable (Claude Code 2.1.318).

Consulting angle

Ask this week: After a runner restart or a session resume, does your coding agent keep exactly the approvals it was granted, no more and no fewer, and can you show that in a log?
