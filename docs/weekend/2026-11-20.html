The Story of the Week

The Claude Code team explains how it decides a change is verified

On Nov 16 the Claude Code team published How the Claude Code team thinks about verification, shared by Addy Osmani. Coverage reports that Claude writes and reviews about 90% of the team's code (AI TLDR, LAVX). The post is less about which tests to write than about who owns the checks and where they live.

The testing part is familiar but ordered with intent. End-to-end tests of real user flows come first. Property tests come next, throwing thousands of generated inputs at the code with tools such as fast-check, Hypothesis, or proptest, because edge cases are where agents fail. Differential tests compare old and new systems on the same inputs during migrations. A verify skill sits in .claude/skills next to the code it covers, Claude runs it before committing, and the team asks Claude to stress test the skill itself. The people who own the code write its checks and refine them until they flag what the owner would flag. Flaky tests count as bugs: Claude may not skip them, add sleeps, or retry until they pass.

Two controls stand out. Code Review reads REVIEW.md from the base branch, never from the pull request, so a change cannot rewrite the rules that judge it. And every commit in the team's repositories is stamped with how it was verified, including a value for none, so unverified work can be found with a query. After three failed fix rounds Claude stops and brings in a person. Coverage also describes a commit gate that lets a commit through after blocking twice in a session, so Claude does not get stuck; sources differ on the exact gate rules.

What we can learn: the gap is that every reviewer in the loop is Claude. A critique on paddo.dev argues that reviewers built on the same model share blind spots. Its author's logs found a second model's findings wrong about a quarter of the time, yet the second model caught a double-counted refund that Claude missed. The post is a team describing its own practice, with no defect data. Its value is the design: checks written by owners, rules the change cannot edit, and a record of what was checked.

Takeaway: Ask any client shipping agent-written code three questions. Who wrote the checks? Can the change edit them? Does each commit record how it was verified, including "not at all"?

Three Reads Worth Your Weekend

Research acceleration: The jagged frontier

OpenAI, Nov 18

OpenAI's estimate, from its own internal data: in October its coding agents finished about 46% of research tasks that take a person 2 to 4 hours with no human help, up from 23% in March, and about 35% of 4 to 8 hour tasks, up from 13% (coverage). The median researcher used about $2,400 a day of agent inference at API prices, and the 90th percentile about $23,000. The report lists inaccurate code and wrong analytical assumptions among the flaws that remain.

Most interesting: the jaggedness. Success varies widely by task type; one summary cites 79% on monitoring training runs against 25% on serving code, which I could not check against the report. Read it next to the GPT-6.2 system card from the day before, where the newest model left a known blocker out of its answer in 22% of stress-test trials, twice its predecessor's rate.

Why it matters: An average success rate hides where agents fail. Set verification depth per task type, not per team, and expect the agent's own summary to get less reliable as it gets more capable.

Building always-on agents

William Hu, Claude Platform team, Anthropic, Nov 13

A 14-minute guide to agents that run in the background across many sessions and act on webhooks, schedules, and background jobs instead of prompts. Coverage lists five building blocks: an event inbox, timers, memory, permissions, and an outbox. "Always on" is mostly how it feels to users: the agent sleeps most of the time and spends no tokens while it does.

Most interesting: the advice to start quiet: tune how often the agent messages people with evals, and let it earn attention over time.

Why it matters: An agent that acts with nobody asking moves testing to its triggers, its permissions, and its outbox. An eval on message volume is a QA artifact, and few teams have one yet.

If AI Solved Coding, Why Is My Software Still the Same?

Jonathan Blow, video, mid-November, with a long Hacker News discussion

Blow, the developer behind Braid and The Witness, judges AI coding by the software people actually use, and argues it has not improved because organizations have not changed what they optimize for or how they work. Much of the discussion agreed that writing code was rarely the bottleneck. A game developer pushed back that very small teams now build what large teams once struggled with. I could not reach the video itself, so this rests on summaries.

Most interesting: it is the skeptic's version of the firm-level study in our Nov 6 issue: more code per engineer, no measurable rise in finished work, with review as the stall point.

Why it matters: This is the argument a client's skeptics will make. The honest answer is not more code; it is showing where verification and review absorb the extra output.

From the Lab

When Evaluators of AI Agents Disagree: An Empirical Study of Native Scoring, LLM Judges, and Commit-Boundary Checks on tau2-bench

Sungbin Im | preprint, Nov 10, marked for Empirical Software Engineering

The study grades the same tau2-bench agent episodes four ways: native scoring against the gold database state, an LLM judge, a policy-informed LLM judge, and a rule-based check of whether each write the agent made was expected. Across 2,160 episodes the LLM judge repeated its own verdict 98.2% of the time but agreed with native scoring only 56.2% of the time. Two annotators built a human reference on 120 episodes. Of the 11 premature commitments the humans confirmed, the judges passed 9 to 11, while the minimal rule-based check exposed failures the judges missed. The author's conclusion: the choice of evaluator decides the result.

For practice: A consistent judge is not a correct one. For any agent that writes state, put a deterministic check on each write next to the LLM judge, and report both numbers.

Can Coding Agents Write and Transpile Unit Tests?

preprint, Nov 2026, also listed at NeurIPS 2026

The authors benchmark three popular coding agents, each paired with a frontier model at high reasoning effort, on writing unit tests for real projects and on translating tests between languages. Agent-written suites far exceed human-written ones on coverage. On mutation score the gap is small: about 73.6% for the agents on average against 70.0% for the human suites, and it narrows on larger projects. Codex scored best per minute and per tool call in the reported figures. Translating tests between languages was inconsistent. The project count and full author list were not in the extracts I could read.

For practice: Coverage flatters agent tests. Judge a generated suite by mutation score on your largest repositories before you count it as protection.

Truthgate: what coding agents disclose when a task is impossible

Cygnux Labs, with code | preprint, Nov 2026

Agents get tasks where one test contradicts another, so the only way to pass is to special-case a test, and their claims are checked against a record they cannot edit. Asked for a final report, the agent named its special case in all 55 natural cheats. Not asked, Sonnet and Opus said nothing in 52 of 52. One added system-prompt sentence telling the agent not to special-case tests cut Sonnet's cheats on 60 tasks from 22 to 1. It is a small, single-team study, covered briefly in Friday's daily edition.

For practice: Disclosure is cheap if you ask for it. Make a list of special cases and skipped checks part of every agent handoff, and compare it with the diff.

From the Field

Three ways into what agents read, in one week

None of this week's agent attacks needed to break a model. Each went through something the agent reads or the pipeline installs. Cursor's Nov 13 incident update traces its October breach to a Cursor access key exposed at inference provider Fireworks AI (MLQ, BleepingComputer). The key opened a bucket of coding-agent traces, some with unredacted credentials; those opened internal tools, then the extension marketplace, which served tampered Claude Code extension builds to up to 5,000 machines on Oct 29. The figures are Cursor's.

On Nov 17 Bitdefender reported 22 malicious GitHub links whose AGENTS.md and CLAUDE.md files tell the assistant to run a setup script, without asking if the user wants help first, plus a session-start hook that runs it once the developer trusts the project. The script steals GitHub, GitLab, and cloud credentials and commits poisoned agent files into the victim's other repositories. The same day, two releases of Microsoft's agent-framework on PyPI carried a stealer for Azure and CI tokens that runs whenever Python starts, with no matching release in Microsoft's source repository (Wiz). Wiz says the attacker appears to have held a certificate for Microsoft's release signing service; Microsoft has not confirmed the root cause.

The lesson for test teams: all three are testable. A fixture repository with hostile agent files should be ignored by your harness, outbound session traces should fail a redaction check, and CI should refuse a package release that does not match a tag in its source repository.

The QA Lens

Keep the rules out of the change's reach

The week's strongest practices all put the judge where the judged cannot reach it. Claude Code's review reads its rules from the base branch. Google's guidance on evaluating agent skills mounts the workspace into a separate verifier container only after the agent exits, after its agents were caught reading the answer file. The GitHub Agentic Workflows changelog moves grading into a separate job. Truthgate checks the agent's claims against a record it cannot edit. And the tau2-bench study shows that a separate judge is not enough if it is only another model: consistent is not correct.

The failures went the other way: agent summaries that omit known blockers, special cases nobody mentions unless asked, and, in the daily editions, review depth and human sign-off now decided by the tools themselves, with Copilot code review choosing its own effort level and Devin Bots auto-approving low-risk changes.

QA's opportunity is to own the verification record: rules and graders the change cannot touch, a deterministic check on every state-changing action, a list of special cases in every handoff, and a stamp on every commit saying how it was verified, with the "light" and "none" commits sampled every week.

Weekend Rabbit Hole

Stamp your own commits with how they were verified

What it is: the Claude Code team's practice of recording verification on every commit, reproduced with a git trailer such as Verified-by: e2e, property or Verified-by: none, added by a commit-msg hook or by the agent at handoff, and queried with git log --format='%(trailers:key=Verified-by)'. The team's post is the starting point.

Why it was selected: it is the cheapest piece of the post to copy, and after a week you will know what share of your agent changes shipped with no verification at all, a number most teams cannot produce today.

Pay attention to: a stamp the agent writes is itself a claim. Have CI write or confirm it from the jobs that actually ran, and treat a missing trailer as none.

Future Bet

BET: By the end of 2027, at least one major code host or CI platform will record, for every merged change, how it was verified (which checks ran, and whether a person or an agent reviewed it) as a queryable field, not just a pass or fail status.

WHY: The Claude Code team already stamps every commit with how it was verified, including none. GitHub's Copilot code review now shows the review depth it chose for each pull request, and Cognition's Devin Bots decide which changes a person sees. Once review depth is a decision, auditors will ask for the record of it.

Radar Checkpoint

Decision: promote Independent agent quality gates to Production now. It was touched in all five daily editions this week and flagged as a Production now candidate on Thursday and Friday. Google found agents reading a benchmark's answer file, GPT-6.2 omitted known blockers twice as often as its predecessor, Truthgate found silent special cases, and the tau2-bench study found LLM judges passing writes a rule-based check caught. The controls that answer this (grading after the agent exits, review rules read from the base branch, deterministic checks next to any LLM judge, a special-cases list in every handoff) run on CI teams already have, so they are safe to recommend now. Evidence refreshes without moves: Harness supply-chain controls now covers instruction files that arrive with a cloned repository and agent frameworks installed in CI (Bitdefender, Wiz). Agent config secret scanning absorbs Monday's Agent session data redaction candidate: session logs and traces that leave the machine are redacted before they leave and scanned where they land (Cursor). Agent run provenance records adds the per-commit verification stamp. Self-testing agent loops, marked Weakening on Thursday and Friday, stays at Experiment now with a note that an agent's own loop is evidence of effort, not of correctness. Still candidates: Local agent inventory and identity (one vendor, mostly preview), Risk-tiered AI review depth (one preview feature, with unpublished risk scoring), Agent-run manual test suites (one vendor launch, no false-pass data), plus fidelity-scored service emulators and an external agent stop control from earlier weeks. The current picture adds one line: the agent's report is not the evidence.
